# 实施记录 —— 计划 vs 实际

> [`设计文档.md`](设计文档.md) 写于 2026-09-13,是**动手之前的计划**。
> 这份文件记录**实施之后实际发生了什么**,尤其是**计划外的东西**。

**为什么这份文件值得留着:**

> 计划写得再细,动手都会偏。**关键不是"有没有偏",是"偏的时候你知不知道自己在偏、偏的理由站不站得住"。**
> 面试时被问"你这个项目是怎么做的",照计划念没有价值 —— 有价值的是"我原本打算 X,做到一半发现有 Y,所以我改成了 Z"。

---

## 一、三处主要分歧

| | 计划里怎么写的 | 实际怎么做的 | 为什么改 |
|---|---|---|---|
| **检索** | 直接上 `Embedding(本地模型)` | 先做**关键词检索基线**,向量留到第 7 课 | 没有基线,"向量更好"这句话永远说不出口:更好?比谁好?好多少? |
| **路由** | **计划里没有这个概念** | 成了整个系统的核心(`route.py` + `route_llm.py`) | 数据住在两个地方(结构化的表 / 非结构化的文档),必须有一层决定"这题去哪查"。计划把它当成了"检索"一个环节,实际它是独立的一层 |
| **拒答** | 列为"实验四:拒答机制对比" | 第 4 课就定性了:**拒答不是一条路,是第一道闸** | 它是"数值型 × 数据不在库"的产物。当成并列选项,就会把库里明明有的数据也拒掉 |

**一句总结分歧的根源:**

> 计划是**照着"一个 RAG 系统应该有什么"写的**;
> 实际是**照着"这个库真实长什么样"做出来的**。
> 真实长什么样,只有跑起来才知道。

## 二、逐课记录

### 第 1 课 · 切片与结构化

**做了什么:** 9 份 PDF → 54 个 text chunk + 3 张结构化表
**产出:** `capse_chunks.jsonl` / `capse_meta.csv`(9 期口径) / `capse_scores.csv`(373 条) / `capse_indicators.csv`(294 条)

**发现的坑:**

| 坑 | 现象 |
|---|---|
| Excel BOM | `utf-8` 读出来第一列名字前面多个不可见字符 → 用 `utf-8-sig` |
| PUA 字符 | PDF 抽出来的文本里混有私有区码位,肉眼看不出来,比对时对不上 |
| 全角加号切断检索 | 原文 `" 数据＋管理" 模式`。搜 `数据＋管理` → 14 条;搜 `数据管理` → **0 条** |
| 年度报告漏了 | `2024年度报告` 文件名里没有季度编号,切片时被跳过 —— **它至今没进库** |

**实测:2023Q3 选中的页码是 5,7,11,12,13,14 —— 跳号是对的。** 6/8/9/10 页因为列了 41 个机场名,被判为"数据页"排除在外。

---

### 第 2 课 · 建库与约束

**做了什么:** 建 SQLite,把约束写进表结构
**产出:** `capse.db` —— meta 9 行 / 综合得分 373 / 指标得分 294

**约束清单:**
- `PRIMARY KEY` —— 同一期同一机场不能出现两次
- `FOREIGN KEY` —— 期次必须在 meta 里存在(**SQLite 默认不检查,必须每个连接手动 `PRAGMA foreign_keys = ON`**)
- `CHECK` —— 口径版本只能是 `6+30 / 6+31 / 7+28`
- **跨列 CHECK** —— `口径版本 = 一级指标数 || '+' || 二级指标数`
- **松约束** —— `CHECK (得分 > 0)`,**不写死范围**(写死 `BETWEEN 3 AND 5` 明天就过期)

**实测:5 条非法插入(口径不在清单 / 口径与指标数不自洽 / 期次不存在 / 得分为负 / 主键重复)—— 全部被拦下。**

> **约束没生效 = 白写。而"生效了没有"不能靠读代码确认,必须拿真实非法数据撞一次。**

---

### 第 3 课 · 检索基线

**做了什么:** FTS5 全文索引 + 检索函数
**产出:** `build_search.py`

**最大的坑 —— 默认配置是坏的,而且不报错:**

```
实测:插入 "2025Q4内地机场综合得分包含测评项目机场交通"
      unicode61(默认)  搜 '机场交通' → 命中 0   ← 静默失败
      trigram           搜 '机场交通' → 命中 1
```

**FTS5 默认分词器把整句中文当成一个词。** 不报错、不警告、就是搜不到。

> **默认配置不等于正确配置。你不主动拿一个已知答案去试,会一直以为它在正常工作。**

**第二个坑 —— 索引会静默变旧:** 用 external content 写法(索引不复制文本)守住了"单一真相源",代价是改了 `chunk` 表**索引不会自动跟着变**。必须显式 `rebuild`。

**还发现:** 必须把"**查不了**"(查询少于 3 字)和"**查了没有**"分开表达 —— 否则调用方会把"工具的限制"说成"知识的缺失"。

### 第 4 课 · 路由

**做了什么:** 决定一道题该走 SQL / 检索 / 拒答
**产出:** `route.py`

**结构(三步,顺序是跑错一次才改对的):**

```
① 要【一个数】还是要【一段话】?      ← 必须最先判,它决定下一步问的是什么
     要数 → ② 这个数在库里吗?  不在 → 拒答 ; 在 → SQL
     要话 → 检索(不需要期次,也不需要事前查"在库吗")
③ 跨口径吗?                        是 → 加标注
```

**两条实测出来的原则:**

> **① 拒答是最贵的选项,不是最安全的。**
> 答错,用户能核对;**拒答错了,用户拿不到数据,而且不会知道。**

> **② 口径差异必须查,不许感觉。**
> 实测:2025Q1→Q4 都是 `7+28`,口径**压根没变过**。
> 凭"感觉变了"去拒答,就是把库里明明有的数据藏起来。

**规则版有多脆(实测):** 用同一件事的 8 种说法去测 —— **错 2 种**。
其中一种**判不出**(看得见),另一种**走错了路**(看不见)。前者是"不够好",后者是"坏了"。

---

### 第 5 课 · 端到端 + 接入大模型

**做了什么:** 库 → 检索 → 路由 → 验证 → 输出,串成一条链;大模型接进两个位置
**产出:** `ask.py` / `llm.py` / `route_llm.py`

**对照结果:**

```
第②步「要数还是要话」    关键词表 12/18   →   大模型 18/18
检索命中                 整句 0 条       →   改写后捞到正确页面
答案带来源               4/10 题         →   10/10 题
```

**大模型只干两件事,一件数据都不产出:**
1. 判"这题要数还是要话"
2. 把问句改写成检索关键词(顺手解决同义词:用户说"调整",原文写"变更")

> **数据全部来自 SQL 查表 / 检索查原文 —— 所以"答案必须带来源"才成立。**
> **如果让模型自己答题,它就没有来源可给,这条规则立刻塌掉。**

**三个计划外的发现:**

| 发现 | 说明 |
|---|---|
| **SQL 也会静默答错** | 问"哪项一级指标最高",它答"综合得分 4.23"。格式漂亮、来源齐全、就是答非所问 |
| **"必须给来源"照出一个缺口** | SQL 的来源只能到**表名**,回不到 PDF 页码(入库时没记)。检索那一路是完整的 |
| **规则判错 ≠ 规则判不出** | 规则命中"如何"→**有把握地**判成检索 → **压根没走到"判不出交给模型"那一步**。而且事后验证也没拦住:回来的页面里**顺带**就有数字 |

**第三条最要命,因为它戳破的是设计本身:**

> "规则先出手、拿不准交给模型" —— **有个没说出口的前提:规则得知道自己什么时候不知道。它不知道。**
>
> **修法:规则只在它不会错的地方出手。** 把"如何""哪些""怎么""几"全删了 —— 它们会错。
