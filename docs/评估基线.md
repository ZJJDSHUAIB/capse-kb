## 一、基线数字


## 二、这个基线是怎么算出来的

```bash
python tools/check_eval.py          # 先核对评估集本身(60/60 可核,0 分歧)
python tools/score_eval.py          # 再拿评估集去问系统 → docs/评估集_跑分.json
python tools/score_eval.py --from-json   # 不重跑调用,直接拿存下的答案重判分
```

**大模型判分有缓存**(`docs/评估集_判分缓存.json`)。重跑时命中缓存的题不重新调用。
⚠ 改了评估集里的【期望答案】,缓存键就变了,那几道会重新调用。

> ⚠ **`score_eval.py` 在 2026-09-17 被有意改过两次**(`359ef163c6` → `fb57d36852` → `f23498a3d3`):
> ① 判分缓存的键用了 Python 内置 `hash()`,而它对字符串**每个进程挂随机盐**,
>    所以缓存一次都没命中过 → 每轮重判 → **判分噪音约 ±1.7 个点**。
>    改成 `hashlib.md5` 之后,同一代码跑两次结果完全一致。
> ② 加了**缓存命中率自报**(`_HIT`),让"缓存失灵"这种事自己浮出来。
> **改动理由和证据见 `docs/实验台账_对比实验.md` 第八、九节。**
> 坏键存档:`docs/评估集_判分缓存_坏键存档.json`(留作证据,不再使用)。

> ★ **本文件的 61.9% 基线,已用固定尺子重测确认仍然成立**(两次一致)。
> 但基线已经移动六次 —— **当前基线是 89.2%**,见《实验台账_对比实验》第十七节。

## 四、改参数的规矩(防止"是撞运气赢的")

1. **一次只改一个变量。** 同时改三处,分数涨了也不知道是谁的功。
2. **每次改完重跑全部 60 道**,不是只跑相关的那几道 —— 你可能修好一类、弄坏另一类。
3. **看类别分数,不看总分。** 总分涨 2 个点可能是"叙述检索涨了 0.5、数值比较跌了 0.3"。
4. **改完要能说出"我预期哪一类会涨、涨多少"。** 说不出来就说明这次改动是瞎试。
   预期落空比分数难看更有信息量 —— 那说明你对系统的理解和系统不一样。
5. **不许改评估集来让分数变好看。** 评估集动了,基线就废了,得从头再来。
6. 每一轮的结果**追加**记到 `docs/实验台账_对比实验.md`,不覆盖 —— 失败的尝试也要留。
