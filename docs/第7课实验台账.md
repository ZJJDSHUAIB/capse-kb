# 第 7 课 · 实验台账

**开课日期:** 2026-09-17
**目的:** 不是"把分数调上去",是**搞清楚每个参数值多少钱**,以及**你怎么知道它是真的**。

> ⚠ **开工第一件事:先跑一遍基线,确认数字对得上,再动任何代码。**
> 对不上就是库或脚本跟冻结时不一样了,先查清楚。
> 这条是规矩不是客套 —— 台账是"某人写的一段话",而**信印象不信查**是这个项目一路在打的病。

## 一、规矩(六条,先认这个再动手)

**① 先跑基线。** 见上。

**② 一次只改一个变量。** 同时改三处,分数涨了也不知道是谁的功。

**③ 从上游往下游改。**

```
route.py(该走哪条路) → build_search.py(怎么找) → ask.py(找到之后怎么给) → build_chunks.py(切什么)
```

**上游一变,下游调好的参数就作废。** 先调 `ask.py` 的 `k`,再给检索加期次过滤 —— `k` 的最优值跟着变,第一次的结果要整个重做。
这不是理论,是从下游开始调的实验最常见的白干:**在流沙上盖房子。**

**④ ★ 故意改坏,看掉多少。**
这是"这个旋钮接上线了吗"的最快问法:

```
改坏 → 跑 60 道 → 看哪一类掉了 / 掉了多少 → 改回来
```

**掉得多的,说明这个旋钮电源插着的;掉不动的,说明它根本没接上线。**
比"猜哪个参数有用"可靠得多 —— 而且一次就能筛出**死参数**。

**⑤ 每次改完,先说出预期。**

> "我预期**叙述·检索**这一类会涨,**大概 0.13 → 0.3**。"

说不出来,就说明这次是瞎试。**预期落空比分数难看更有信息量** —— 那说明你对系统的理解和系统不一样,那才是真的学到东西。

**⑥ 不许为了让分数变好看去改评估集。** 评估集动了,基线就废了,得从头再来。
每一轮结果**追加**记到本文件,**不覆盖** —— 失败的尝试也要留。

### 实验 1:把「点名段落」做进路由

改的是：`tools/route.py`
- 新增 `DOC_SECTION` 正则(约 92 行):`(?:报告|概况|简介|说明|声明|测评|简报|名录|附录)里`
- 第①步新增 `doc_section` 分支(约 213 行),排在 `NUMERIC`/`PROSE` **之前**
  - 旧:`wants_num = bool(indicator) or NUMERIC.search(q)`,`wants_prose = PROSE.search(q)`
    —— 两张词表,数词优先
  - 新:问题点名了报告的某一段落(…里)→ 直接判"要话",**数词在这里不参与**
  - 幅度:1 个变量(1 条新规则),但落在 2 处(正则定义 + 判断分支)

改了 md5:`route.py` `11d85b3ac1` → `12d534cbde`

为什么改：`route.py` 的 8 个错决定里,5 个是**检索题被数值词表抢走**(#43 #44 #46 #47 #48)。
它们问的是"报告概况里 / 分吞吐量级服务测评里",答案印在**页**上,
而 `#43` 只带了"多少"两个字就被拖去 SQL —— 库里根本没有"一级指标数"这一列。

**为什么是"一条规则"而不是"往词表里加词"(这是本轮最要紧的一步):**
往 `PROSE` 里补"概况""吞吐量级",下一批问法("报告讲了些啥""那一页写了什么")
照样漏 —— 那是第 5 课判定过的跑步机。而"**…里**"不是"用户用了哪个词",
是"**用户在指一段文档**":X里 = 答案住在那段文字里,不住在表格格子里。
这是说法背后的**结构**,只有一种形状,不会随问法变体无限增殖。

证据(先查再改,没靠印象):


| | 预期 | 实际 | |

## 八、★ 量具事故:判分缓存从来没有生效过

**这一节不是"改了什么参数",是"尺子本身坏了"。它比实验 2 的结论重要得多。**

### 8.1 怎么发现的

我按规矩把 K 改回 3,想恢复干净状态,结果跑出来 **65.2%** ——
而实验 1 记的是 **66.9%**。**同一份代码、同一个库、同一个判分脚本,两次不同的分。**

先排除"文件被动过":ask.py `e596d15f4a`、route.py `12d534cbde`、capse.db `418b3f36d7`
—— 三个全部与记录一致。**所以差异是跑出来的,不是改出来的。**

### 8.2 定位:飘的是尺子,不是系统

连跑 3 次,把飘的那道题(题 46)摊开:

```
       检索用词                                        来源
第2次  2025Q4 吞吐量 服务测评 机场 综合得分 4000万级     2025Q4-P19/P18/P07
第3次  2025Q4 吞吐量 服务测评 4000万级 机场 综合得分 排名  2025Q4-P19/P18/P07
第4次  2025Q4 吞吐量 服务测评 4000万级 机场 综合得分       2025Q4-P19/P18/P07
```

检索结果一模一样。再看系统答案文本:

```
第2次  长度=365  md5=f6a21b13
第3次  长度=365  md5=f6a21b13     ← 三次逐字相同
第4次  长度=365  md5=f6a21b13
```

**系统答案逐字相同,却被判出了两种结果。→ 飘的是判分用的大模型。**

### 8.3 根因:缓存键用了 Python 内置 `hash()`

```python
key = f"{row['题号']}|{hash(str(row['期望答案']))}|{hash(got_a)}"   ← 旧
```

**Python 的 `hash()` 对字符串每个进程都挂一个随机盐。**

```
$ python -c "print(hash('2025Q4-P18'))"
第一次 1173152066846808461
第二次 7520943737700370646      ← 同一个字符串,每次都不一样
第三次 1483649548913095925
```

→ **缓存键每轮都变 → 这个缓存一次都没命中过。**

**旁证(我当时看见了却没反应过来):** 数缓存文件时,#38 一道题有 **7 条一模一样的记录**
—— 那是它被重复判了 7 次的痕迹,不是 7 个不同的结论。

### 8.4 后果

- 每道判过的题,**每一轮都重新调用一次大模型**(白花钱、白花时间)
- 每次调用都是一次重新掷骰子 → **判分噪音约 ±1.7 个点**(实测 4 次:3 次 66.9%,1 次 65.2%)
- **在此之前的所有分数,都带着这个噪音**

### 8.5 修复与验证

改一行 + 加一个 import:

```python
import sys, io, re, sqlite3, json, argparse, hashlib
_k = lambda s: hashlib.md5(str(s).encode('utf-8')).hexdigest()[:12]
key = f"{row['题号']}|{_k(row['期望答案'])}|{_k(got_a)}"
```

- 坏键存档:`docs/评估集_判分缓存_坏键存档.json`(留作证据,不再使用)
- 清空缓存后跑两次,**两次完全一致**

md5 变化:`score_eval.py` `359ef163c6` → `fb57d36852`(**有意修改,不是误改**)

### 8.6 ★ 修正后的真数(用固定尺子重测)

| | 原记录(坏尺子) | **重测(固定尺子)** | |
|---|---|---|---|
| 基线 | 61.9% (32/60) | **61.9% (32/60)** | ✅ **原记录就是对的**,两次一致 |
| 实验 1 | 66.9% (35/60) | **65.2% (34/60)** | ★ **原记录是一次走运** |

### 8.7 这件事本身是第 7 课最好的教材

**"怎么知道是撞运气赢的?"** —— 这一节就是答案的前半截:

> 你以为你在量系统,**其实你的尺子自己会抖**。

**答案里同时出现几段互相排斥的话。** 用户读到自相矛盾,判分判它错。

→ **上一轮 #42 那个反例,在这里变成了一般规律:**

> **多拿不是纯收益。多拿的每一条,既可能是答案,也可能是噪音 ——**
> **而噪音不是"没用",是"有害"。**

## 十一、实验 4:把「答案」和「摘要」分开(修 `ask.py:235` 的 `[:120]`)

**这一轮换了顺序。** 原计划做期次过滤,改成了先修截断,理由(张君杰认可):

1. **期次过滤的收益骑在噪音上。** 逐题算完只有 #42(满分)+ #40(半分)= +1.5 分 = +2.5 点,
   而判分噪音是 ±1.7 点。**但它的过程指标(污染率 33%→0)会显示成一场大胜。**
2. **修截断的收益是 +3 道 = +5.0 点**(是噪音的 3 倍),成本一行。
3. ★ **顺序的真正理由:基线干净。** 效果 = 改后 − 改前,而现在的"改前"里有 3 道题的分数
   **不反映检索质量**(被一个无关原因压成 0)。**分母脏了,差值就不可信。**
   不先修,期次过滤的收益会被算成 #40 的半分 → **低估它**。
4. **截断是已知 bug,期次过滤是新功能。修 bug 优先于做 feature** —— bug 会污染所有后续测量。

### 11.1 改法:不是"把 120 改大",是"把两个身份分开"

```python
# 改前(ask.py:235)
out["答案"] = [h["文本"][:120] + "…" for h in hits]

# 改后
out["答案"] = [h["文本"] for h in hits]        # 答案:完整原文,给判分和下游用
# render() 里:
print(f"    {line[:120]}" + ("…" if len(line) > 120 else ""))   # 摘要:只给终端显示用
```

**病根不是"120 太小",是同一个字段有两个身份。** 把 120 改成 500 只是把阈值挪个地方,
换一批题照样被砍。**分开之后,以后 k 调大、切片变细,都不会再有人踩到它。**

md5:`ask.py` `e596d15f4a` → **`2706fea303`**

### 11.2 结果(跑两次一致)

## 十四、指标 8/9:告警率 —— 先立尺子,还没改系统

**张君杰问:"还有什么指标吗?"** —— 这一节是答案。
**这一轮【不写功能】,只加指标。所以总分必须一动不动。**

### 14.1 为什么加这个

**量出来的第一件事(60 道题,任何警告的总数):**

```
答错/不全 16 道 → 系统报了 0 次警告
答对     44 道 → 系统报了 0 次警告
全 60 道        → 0 次
```

**它不是"很少报警",是从来没报过。** 而判分脚本从头到尾**没算过这个数**。

**这个 2×2 从来没被算过:**

```
                  有警告       无警告
  实际错误/不全    真阳性      ★ 静默失败   ← 最贵的一格
  实际正确       ★ 误报         正常
```

### 14.2 口径(张君杰定的)

```
指标 8  错误告警率 = 答错/答不全的题里报了警告的 ÷ 同类题总数
指标 9  误报率     = 答对的题里报了警告的 ÷ 同类题总数

※ 分母不用 60 —— 这个指标测的是「系统犯错后意识到自己错了的概率」,
  不是「60 道里有多少道有警告」。该拒答的留在『拒答两个方向』里,不混进来。
※ 第一版警告按【非空/空】二值判。
※ ★ 暂不设阈值。他原话:"10% 的依据是什么?如果没有业务依据,容易变成人为拍的门槛。"
※ 必须【同时】卡误报 —— 否则"每道题都报警"能拿 100%,但系统完全不可用。
```

### 14.3 ★ 我加的一条:必须【按路径分层报】

**先纠正我自己说过的一句错话:** 我说过"SQL 结构上不可能报警"。
**不对 —— 不是结构上不可能,是那条路上【一个检查都没写】。**

整个 `ask.py` 里只有两处会写警告(`ask.py:315` 判不出 / `ask.py:380` 检索的 verify),
而且检索那道 `verify()` 查的是**「这题该不该走检索」**(路由检查),**不是「这个答案可不可信」**。

> **真相更硬:整个系统里,没有一处检查「这个答案靠不靠得住」。**

**不分层的话,这两个数会被"SQL 占多少比例"埋掉:**

```
错误告警率 分母 16 道:SQL 11 + 检索 5   → 上限只有  5/16 = 31%
误报率     分母 44 道:SQL 26 + 检索 11 + 拒答 7 → 上限只有 11/44 = 25%
```

**层一分,"检索 0/5"一眼可见 —— 那才是「有机制却不用」的证据。**

### 14.4 基准值(跑两次一致)

```
★ 指标 8/9:告警率(按路径分层)
    答错/不全(错误告警率)  0/16 = 0%
        SQL   0/11
        检索   0/5        ← 有 verify 机制,一次没触发
```

**总分 81.9%,一动没动 —— 正是应该的。加指标只改"看得见什么",不改系统。**

**分母的线是 `<1.0`(不满分即计入),这是【口径】不是随手取的:**
换成 `<0.5`,分母就从 16 掉到 10。**线要人定,不能默认。**

md5:`score_eval.py` `baf1141592` → `750754d6ba`

### 14.5 ★ SQL 那条路错了怎么办 —— 现在是没办法

```
               检索答错              SQL 答错
用户看到       几段【原文】          一个【数字】+ 表名
能不能自己判断  能(原文在那儿)      不能(没有原文可对照)

```

## 二十、实验 11(未做)+ ★ 三次撞在同一堵墙上

### 20.1 想调的旋钮:多词合并规则

```python
# build_search.py:169-177  search_multi()
#   注释:"每个词各返回一批,同一个 chunk 被多个词命中 —— 算它的最好成绩
```

**★ 注释说的和代码做的不是一回事:**

**所以该对照的不是 min → max(max 是反着来,几乎肯定更差),是 min → sum。**

**方向一致,而且正是想要的方向:P07 概况页被挤下去。**

**但分数【一分不变】—— #38 和 #47 现在都已经是 1.00**(正确页本来就在前三)。
**而真正的目标那三道(#48 #51 #52),min 和 sum 一模一样 —— P21 还是第五,K=3 取不到。**

### 20.3 顺带证实:那段注释的直觉是错的

**实测:P07 概况页就是靠"被多词命中"稳排第一的** —— 而它恰恰是最不相关的那一类
(每期都有一份、内容几乎一样)。

```
2025Q4-P07   被 3 个词命中  [-3.31, -1.15, -1.29]  min=-3.31  ← 稳排第一
2025Q4-P21   被 2 个词命中  [-2.36, -1.62]         min=-2.36  ← 第五名,取不到
```

**改成 sum 把 P07 挤到第三 —— 说明 sum 在这个点上更接近对的。但还不够,P07 还在前三。**

### 20.4 ★★ 三次撞在同一堵墙上(这一轮真正的结论)

```
实验 9   SQL 告警率        →  碰不到:没有分母(60 道题撞不到 SQL 的软肋)
实验 10  max_tokens 80    →  碰不到:输出 14~35 字,上限 80,从没顶到
实验 11  min → sum        →  ✅ 碰得到【排序】,❌ 碰不到【分数】
```

> **而我们的指标,全部是"分数"。**
> **所以一个"让排序变好、但还没好到能得分"的改动,这套评估看不见。**

**→ 现在最缺的不是改动,是量具。**

**规矩补一条(第 ⑨ 条):**
> **做一个改动之前,先问:「我的量具够得着它吗?」**
> 够不着的实验不该做 —— 不是因为它没价值,是因为**它的结论【什么都证明不了】**
> (max_tokens 那次:"80 和 40 一样"只说明这 60 道题没顶到,不说明参数是死的)。
> **张君杰那句质疑就是这个:"这只是在 60 个问题里没触及到最大长度。"**

## 二十一、实验 12:告警率第一次动起来(硬限定词)

### 21.1 先纠正一个说法:不是"察觉不到",是"抽错了东西"

**实验 7 我撤掉那个检查的理由是"它测的是错的东西"。查完之后,准确的说法是:**

```
该抽的是「限定词」  1000万-1500万级      ← 【限定】,出现了就是兑现了
```

**「分吞吐量级服务测评」是用户对那一块的【描述】;「1000万-1500万级」才是他要的那一档。**

### 21.2 判据:用户点名的硬限定词,检索兑现了吗

```python
LIMIT = re.compile(r'\d+万\s*[-~]\s*\d+万|\d+万级以上|\d+万级|CAPSE|[一-鿿]{2,6}(?:声明|简介)')
```

判它没事 = 假装查过了(幻觉)。**

**实测六道(在写代码之前量的):**

```
47 2500万-4000万    页里有 → 不报     52 测评简介        页里没有 → 报警 ✅
```

**报的正好是三道真错,不报的正好是三道答对。**

### 21.3 ★ 装上之后的第一次非零

```
错误告警率  0/5  →  3/5 = 60%
误报率      0/55 →  0/55 = 0%     ← 检索路径 11 道答对的,一道都没误报
总分 91.7% 不变(告警不改分数)
```

|---|---|---|
| 实验 7 | 「段落名」(描述) | 3 真 **2 假** = 精度 60% |
| 实验 12 | 「硬限定词」(限定) | 3 真 **0 假** = 精度 **100%** |

md5:`route.py` `827d793aae` → `5999cdc69b`

**① 过拟合嫌疑(最要紧的)。**
这个 6/6 是**在【它被设计出来的那个集】上量的** —— 先想出"限定词"这个概念,再拿这 6 道验。

**② 样本极小。** 5 道错、11 道对。60% 和 100% 这两个数,差一道题就变。

**"仍然静默"这一栏,正是张君杰同意要加的** —— 主指标告诉你进步了多少,

## 二十二、挑战集:验那条规则是不是"记住答案"

### 22.1 它为什么必须存在

**我给「硬限定词」写了一条规则,然后在【同一套 60 题】上量出"3 真 0 假"。**

**那是个不能信的数** —— 我是**先看到 #48 #51 #52**,才想出那条规则的。
**那不叫"规则",那叫"记住答案"。**

要分清只有一条路:**拿一批【没参与设计】的题去撞。**

### 22.2 它的判据为什么是硬的

```
正确的那一页(X)在不在系统取到的来源里?
    ✅ 答对          取到了正确页
    ★ 静默          没取到、也没出声        ← 最贵
    ◐ 出声未答对     没取到、但出声了
    ★ 误报          取到了却还报警
```

**只比对 chunk_id,完全不看那条 LIMIT 规则** —— 所以它答得了"规则有没有过拟合"。

**★ 口径(张君杰定的):「算出声,但不算正确答案」。**
出声有三种,都算:拒答 / 检索·0条 / 警告非空。**而它们都不算答对。**
→ 出声归告警率,答对归正确率;**拒答在这两个数里结果相反,正说明必须分开。**

### 22.3 第一轮:38 道 —— 结果,以及一个我自己差点搞错的地方

```
正式 60 题   精确率 3/3 = 100%   召回率 3/5 = 60%
挑战集       精确率 6/6 = 100%   召回率 6/9 = 67%
```

**→ 两边一样:没有过拟合。** 这条规则在没见过的题上表现没变差。

**但挑战集抓到 3 道静默,全是同一类:**
```
「2023Q3的CAPSE说的是什么」    正确页 P05   取到 P07/P11/P13
「2024Q3的CAPSE是什么」       正确页 P05   取到 P07/P11/P13
「2025Q4报告中CAPSE的内容是什么」正确页 P23   取到 P07/P19/P20
```

**我第一反应是"检查被绕过去了"** —— 因为 `verify()` 的 docstring 里正好写着这句话。
**但查下去发现:是我搞错了。**

```
「CAPSE」   在库里 50/54 页   ← 到处都有,它根本【当不了限定词】
「法律声明」 在库里  9/54 页
「测评指标」 在库里  5/54 页

「4000万级以上」  1/54 页  ✅
「1000万-1500万」 1/54 页  ✅
「2500万-4000万」 1/54 页  ✅
```

**一个到处都有的词不构成"限定"。拿它当判据当然永远不报 ——
但那不是"检查失效",是【这个词没有区分力】。**
**→ 是【题出得不好】,不是【规则漏报】。**

### 22.4 修生成器:加一道【专有性门槛】

```python
MAX_PAGES = 3
def distinctive(con, w):
    return con.execute("SELECT COUNT(*) FROM chunk WHERE 文本 LIKE ?", (f'%{w}%',)).fetchone()[0] <= MAX_PAGES
```

**门槛是量出来的,不是我拍的**:三个真限定词在库里都是 **1/54 页**。

**⚠ 代价:A/B 从 14+14 掉到 4+4** —— 因为够专有的词本来就少,而且全集中在 2025Q4 的数据页。
**样本太小,这是这个挑战集现在最大的弱点。**

### 22.5 第二轮(4 道 A)

```
✅ 答对            1
◐ 出声未答对       3   (全是拒答)
★ 静默            0   ← 关键
★ 误报            0

告警率 3/3 = 100%      精确率 3/3 = 100%
```

**→ 静默清零,而且没有误报。**

### 22.6 ★ 第二轮抓到一个真洞(B 部分)

```
问:「2025Q4的2200万说的是什么」 → 去向=检索,答了 P07 的内容,【没出声】★
```

**LIMIT 只认「XX万级」,不认「XX万」。**
→ 用户问"1500万"而不是"1500万级"时,这条规则不认,于是不检查、不报警。

**这是个真漏报 —— 而且是被【自动生成的题】撞出来的,不是我想到的。**

### 22.7 我犯的错(记着)

**① 第一轮我把"题出得不好"当成了"规则漏报"。**
差一点就去"修规则"了 —— 而规则没问题,是生成器抽了个没有区分力的词。
**查证救了我:一句 `COUNT(*)` 就能分清这两件事。**

**② 遗留:样本太小(4 道)。** 够专有的词在库里就那么几个,而且集中在一期。
**要真正验规则,需要更多"专有但没参与设计"的词 —— 那需要更大的语料,不是更聪明的脚本。**

# 第 8 课 · 报告生成工作流

## 二十三、先量「报告每一节,系统能负责到什么程度」

### 23.1 为什么不先写生成器

**一份报告会放大两件事,方向不同:**
```
放大【错误的绝对数量】  30 个数字 × 8% 错 → 大概 2~3 个错
放大【错误的影响力】    问答里用户会追问;报告里数字直接变成结论
```

**所以门槛不是 91.7%,是:「一份报告里,有多少数字是【错的、而且没标出来的】」。**
→ 先量报告每一节的数据,系统能不能保证。

**张君杰给的 5 节:** ①总体表现 ②核心指标 ③变化与对比 ④问题与亮点 ⑤结论与建议

### 23.2 第一次量出来的结果:**前四节全"核不了原文"**

```
1 总体表现   拿到 2   能核原文 0   ⚠
2 核心指标   拿到 1   能核原文 0   ⚠
3 变化与对比  拿到 2   能核原文 0   ⚠
4 问题与亮点  拿到 1   能核原文 0   ⚠
```

**根因:SQL 那条路的来源只到表名**(`capse.db / 综合得分 表,期次=…`)——
**这是第 5 课就发现、一直没修的洞。**

### 23.3 ★★ 为什么核不了 —— **一个下划线**

```python
# build_scores_table.py          改之前:
_, pairs, _ = extract(f)          # ← extract 返回的第一个就是【页号】,被 _ 丢了

# build_indicators_table.py      改之前:
for indicator, pairs, _page_i in extract(pdf_path):   # ← _page_i,同一个病
```

**而 `extract()` 一直返回 `(页号, [(机场,得分)], 自报平均)` —— 页号一直在那儿。**

> **不是"没算",是"算出来了、写代码的人觉得用不上,就扔了"。**
> **而那个判断在当时是对的**(来源只写到表名就够了)。
> **用途变了,而那两个下划线没人回头看一眼。** —— 这是这个项目第 N 次同一个病了。

### 23.4 补法:几乎零成本

```
① build_scores_table.py     接住页号 → CSV 加「来源chunk」列
② build_indicators_table.py 同上(把 _page_i 改成 page_i)
③ build_db.py               两张表各加一列 来源 TEXT,INSERT 带上
④ ask.py                    来源那一栏改写:…  → 原文 2025Q4-P09
```

**写法跟 `chunk_id` 一致,能直接接到"来源"那一栏。**

**⚠ 踩到的坑(记着):**
- **改列数会让解包错位** —— `for a, s in rows[:5]` 在 SELECT 多一列之后直接崩
  (`ValueError: too many values to unpack`)。**三处都得改成用下标。**
  **而"错位不报错"的那种才最危险** —— 这次运气好,它崩了。

### 23.5 结果

```
回填:373/373 和 294/294 行都有来源,零空值
评估集重跑:91.7% / 告警率 3/5 / 误报 0 —— 【和改动前一模一样,没弄坏】
报告五节:全部"能核原文"  ✅
```

**md5 变化:** `build_scores_table.py` / `build_indicators_table.py` / `build_db.py` / `ask.py` /
`capse.db`(schema 变了,必须重建)

### 23.6 ★ 两个必须说清的保留

**① 第 5 节那个 ✅ 是假的。**
```
问:「为什么浦东 2025Q4 的表现是这样」
答:P18 的得分表原文 + P07 的概况原文
```
**来源对,但【答非所问】。** 用户问"为什么",系统贴了**原料**,没给**结论**。
→ **判据里缺一栏"答的是不是那个问题",而那一栏要人看。**
→ **"结论与建议"这一节,系统现在做不了 —— 它只会【查】,不会【推】。**

**② 我的测量脚本判据过时了。**
它用「来源里有没有 `capse.db`」判"只到表名" —— 回填之后来源**两样都有**,于是永远判"核不了"。
**改成看"有没有 chunk_id 格式的引用"才对。**

## 二十四、报告生成:硬算 + 软说 + 硬查

### 24.1 张君杰问:「这是硬编码吗?就不能像人一样理解文本然后回答吗?」

**答案不是二选一,是【分工】:**

```
代码管   「说什么数」        ← 硬,可核
大模型管 「怎么把数说成话」   ← 软,但它只能用手里的数
代码再查 「数有没有出处」     ← 硬,把关
```

**为什么不能全给大模型:** 报告里的"编"是最贵的失败 ——
问答里用户会追问,报告里数字直接变成结论,没人会核。

### 24.2 补原料:机场分档(`tools/build_tiers_table.py`)

**张君杰问「为什么浦东 2025Q4 的表现是这样」,系统答不出。查下去发现"推"需要的对比基准
【只印在 PDF 的文本里,从来没进过库】:**

```
2025Q4-P18  「…4.13 平均, 4.15北京大兴国际机场…」   ← 4000万级以上,平均 4.13
2025Q4-P19  「…4.11 平均, …」                        ← 2500万-4000万级,平均 4.11
2025Q4-P20  「…4.09 平均, …」                        ← 1500万-2500万级,平均 4.09
2025Q4-P21  「…4.05平均, …」                         ← 1000万-1500万级,平均 4.05
```

**而"浦东属哪一档"连字段都没有。拿【全部机场的平均】去比会得出错的结论。**

→ 新建 `机场分档(期次, 机场, 档位, 行业平均, 来源)`,42 家,**每家恰好一档,一个不漏**(自检保证)。

**⚠ 局限:分档数据只有 2025Q4 一期有。别的期次只能用【上期】和【全体】两种比法。**

### 24.3 硬算:`tools/report_data.py`(三种比法,张君杰选的「丁」)

```
① 同档   浦东 4.23 / 同档平均 4.13 / 同档内第 4(共 11 家)
② 上期   4.23 vs 2025Q3 的 4.23 → 差 +0.00
③ 全体   4.23,在 42 家里第 5
+ 逐指标:  每项的「比全体均值」和「比同档均值」
```

**★ 比错了组,结论会反:** 浦东在【全体】第 5 看着很好,在【同档 11 家】只第 4 —— 因为它那档本来就是强档。

**★ 每条数据带两样:`value`(数值)+ `src`(从哪来)。** 后面那道硬查靠的就是 src。
**★ 我自己算的,`src` 里写清"自算",不冒充报告里印的。**

### 24.4 软说 + 硬查:`tools/report_gen.py`

**Prompt 里五条硬约束**(数字必须来自数据 / 没有就不写 / 用给的 src /
「自算」要标明 / 全体与同档结论相反时两个都要说)。

**★ 硬查:报告里出现的每一个数字,在数据里找得到吗?**
→ **这是这个项目第三次用同一个形状:**
```
第 7 课  检索答错了  → 报警(正确页在不在来源里)
挑战集   规则漏了    → 报警(正确页在不在取到的页里)
现在     报告里的数  → 报警(数据里有没有这个数)
```
**都是同一件事:让"说不出出处的"东西自己冒出来。**

### 24.5 结果

```
报告生成成功,四处出处齐全,「自算」都标了,
全体/同档结论相反的地方两个都说了
★ 硬查:✅ 全部有据 —— 报告里没有一个数是它自己造的
```

**★ 而且大模型自己修掉了一个歧义:**
硬算那版说「最强:航班不正常保障 3.46」(3.46 其实是最低的),而它写成
「**虽为各指标中最低,但比全体均值高 0.27**」—— **有完整数据时它处理对了。**

**硬查第一版报了一堆假的"找不到":**

## 二十五、报告第 5 节:结论与建议 —— **让大模型下结论,但整节声明为「推断」**

### 25.1 这一节和前四节的写法【不一样】

**前四节是「把查到的数据说成话」;第 5 节是「从数据里得出新判断」。**

**而新判断天然不是"有据"的** —— 它是推出来的,不是查出来的。
所以硬查那一套(每个数在不在数据里)对它**不适用**:它可能一个数都不提,但结论是错的。

### 25.2 ★ 我试过"逐句查依据",撤了 —— 而且错在根上

```
原设计:把第 5 节切成一句句,查每条【有没有写"依据:"】

它没用。实测:
   · "## 第 5 节:结论与建议"   被当成一条陈述(那是标题)
   · "最该盯的是机场商贸——它是全部指标中的最低分"
     这句话【本身就是依据】,只是没写"依据:"两个字
   · 我在用「有没有某两个汉字」把守一段【自由的话】
```

**而就算它准了,方向也是错的:**

> **强制每条写「依据:…」,会让"结论"退化成"填表"。**
> **第 5 节之所以值钱,恰恰因为它是在【说话】。框死了就没有结论了。**

### 25.3 正确的做法:**分的是【节】,不是【句】**

```
前四节  →  事实。硬查得住:每个数字在不在数据里。
第 5 节  →  推断。**整节声明,不混进事实。**
```

**用户读到第 5 节,知道那是"系统的判断",不是"数据说的"。**

### 25.4 结果

**大模型写出来的第 5 节质量很好:**
- 每条结论后面挂了具体依据:`(依据:综合得分 4.23,同档排名 4/11,全体排名 5/42)`
- 推断标了「(推断)」
- **判不了的直接说"数据不足,无法判断"** —— 有 6 处

**★ 而且它自己抓到一个我没想到的细节:**
```
机场商贸 3.74 是"最弱的",但航班不正常保障 3.46 数值更低 ——
它解释了自己为什么把商贸当短板:因为航班不正常保障【相对同档反而是优势】。
```
**那是"绝对最低"和"相对最弱"的区别 —— 我的硬算那版把它混在一起了(说「最强:3.46」)。**

### 25.5 ★ 我犯的错(这一课第五次同类)

**硬查在这一节又假报了两轮:**
```
第一轮  ['09','10','2025','3','4000']  ← 从 "2025Q4-P09" / "2025Q3" / "4000万级以上" 里切出来
第二轮  ['1','2','6','7','8']          ← 从加粗编号 "**1.**" 里切出来
第三轮  ['1','2','6']                  ← 「第 1 名」这类【序数】—— 这一轮我【没修】
```

**第三轮我停手了,理由是边际收益递减** —— 序数和数据在文本里分不开,要分开得理解句子。
**诚实地说:这道硬查有已知的假阳性,它会把"第 1 名"里的 1 报成"数据里没有的数"。**

> **判据跟不上文本形状 —— 这一课第五次了。**
> (缓存 hash、`[:160]`、来源判据、收数器只收数值型、这次的序数)

### 25.6 报告到此的完整状态

```
第 1~4 节   数据 + 三种比法 + 出处     →  硬查得住 ✅
第 5 节     推  断                     →  整节声明,硬查查不了(如实说)
```

**★ 而这正是那个分工的完整落地:**
```
代码管   「说什么数」        ← 硬,可核
大模型管 「怎么把数说成话」   ← 软,只能用手里的数
    再管 「下什么结论」       ← 软,而且【标明是推断】
代码再查 「数有没有出处」     ← 硬,把关
```

## 二十七、「拒答也要有用」(张君杰:"不要让系统太死板")

### 27.1 他这条要求,正好指向我刚做的事

**我上一条刚加完 C1/C2 那两条"认不出就拒答"。而他说"别太死板"。**

```

```

```
③ 机场认不出 → 给【同城的机场】。同城是从库里搜出来的,不是猜的:
      「合肥骆岗机场」→ 「库里合肥的机场有:合肥新桥国际机场 —— 你要的是其中一个吗?」
```

**门槛 0.45 是量出来的**:「行李服务」对「出港服务」是 0.50,「靠桥率」对任何指标是 0.00。
**不够像就不给 —— 不给候选好过给错候选。**

## 三十一、★★ 一次"停下来查证"救回来的事故:来源不是 chunk_id

### 31.1 我本来是去做 meta 回填的

**报告的"数据从哪来"那张表里,指标数标着 `⚠ meta 表没回填页码,核不了` —— 我想去补它。**

**先验了一下:逐页找能不能定位那几个数。能,而且值全对。**
**但顺手多查了一句:那些页在库里吗?**

### 31.2 ★★★ 查出来的东西,比 meta 回填重要得多

```
库里 2023Q3 有:P05 P07 P11 P12 P13 P14
而 meta 的数来自:P04(指标数) / P06(样本量、机场数)
→ ★ 两页【都不在库里】—— 因为 build_chunks.py 把它们判成"数据页",整页不进向量库

★ 那第 8 课回填的那些"来源"呢?
   综合得分 表里 9 个来源,【库里一个都没有】。
   它们指向的是 2025Q4-P09 这样的页码 —— 而库里 2025Q4 只有 P07/P18~P21/P23~P26。
```

### 31.3 所以它不是错,是**【没说清】**

```
用户拿它翻 PDF      →  ✅ 有效(页码是对的,能翻到)
程序拿它找 chunk    →  ❌ 找不到(数据页从来没进库)
```

**★ 而它长得和 chunk_id 一模一样(`2025Q4-P09`)——
于是没人能看出"这两个是两回事"。**

> **★★ 在这一课里,"没说清"是最贵的那种错。**
> **一路在打的"看不出区别",这次出现在【格式】上。**
> **而格式产生的歧义,比缺信息更危险 —— 一个假的 chunk_id 会让人以为能程序化追溯。**

**这正是那条规矩的反面应用:「格式该迁就人,只要不产生歧义」—— 而这里恰恰产生了歧义。**

### 31.4 修法:把两种东西写成两种样子

```python
def _pdf(p):
    """把 `2025Q4-P09` 写成 `2025Q4 第9页`。"""
    m = re.match(r"(\d{4}Q\d)-P(\d+)", str(p or ""))
    return f"{m.group(1)} 第{int(m.group(2))}页" if m else str(p)
```

**改前:`capse.db / 综合得分 表,… → 原文 2025Q4-P09`**
**改后:`capse.db / 综合得分 表,… → PDF 2025Q4 第9页`**

**★ 现在一眼能看出:那是【PDF 的页码】,不是库里的块。**

### 31.5 结果

```
评估集:95.0% 不变(去向对 60/60)
报告:  硬查前四节 ✅ 全部有据 / 第5节 ✅ 全部有据
```

**⚠ meta 回填【没做】—— 因为它的页也不在库里,做了措辞还是一样。**
**而措辞说清之后,"meta 没来源"这件事现在可以如实写:**

> 「这几个数来自 PDF 的某一页,但那一页是数据页,没进向量库 —— 所以它只能人翻,不能程序追。」

**★ 这比"回填一个假的 chunk_id"诚实得多。**
