# CAPSE 满意度知识库 —— 项目设计方案

**版本**:v2.0(基于二次修订要求重写)
**日期**:2026-09-13
**用途**:2027 届秋招求职作品(AI 应用 / AI 产品 / AI 运营 / 数据运营方向)

---

## 一、项目定位

> 面向民航满意度分析场景,独立设计并实现 AI 知识库、问答与报告生成工作流,并建立从**检索质量、生成质量到业务效率**的评测体系,通过对比实验定位问题并迭代方案。

**项目重点不在 RAG 代码复杂度,而在于建立面向真实业务场景的评测与迭代闭环。**

要证明的不是"我会用 AI",而是:

> **我能把 AI 用到业务里,并且能对 AI 应用的效果负责。**

定位边界(诚实说明):
- 它是求职作品 / 学习项目,**不是有商业价值的产品**
- 技术实现保持入门级,不堆框架
- 价值体现在方法论与评测严谨性上

---

## 二、项目目标

### 2.1 功能目标
1. 建成一个民航满意度知识库(可问答、可追溯来源)
2. 实现报告生成工作流(输入机场名 → 输出带数据引用的报告初稿)
3. 建立完整评测体系,能回答"效果好不好、好在哪、差在哪"

### 2.2 关于数值目标的重要说明

**本项目不预设"准确率达到 X%"这类目标。**

原因:预设目标会诱导为了达标而反复调参,结论失去可信度。

**改为**:在**固定测试集 + 固定评价标准**下,对不同方案做对比实验,**由实验结果决定最终数值**。

例:可能得到 A 方案 Recall@5 = 58%、B = 74%、C = 86%。86% 是实验结论,不是预设目标。

**完成标准**改为定性:
- [ ] 对比实验完整执行,结论明确
- [ ] 每个方案选择都有数据支撑
- [ ] 失败案例可解释(而非"不知道为什么错")
- [ ] 迭代记录完整,能说清每次修改的理由

## 三、系统架构

```text
公开满意度资料
      ↓
数据清洗 / 文档规整
      ↓
Chunking（3 种策略）
      ↓
Embedding（本地模型）
      ↓
ChromaDB
      ↓
┌───────────────────────┐
│       Retrieval       │  ← Recall@K / Context Precision
└───────────┬───────────┘
            ↓
       DeepSeek LLM
            ↓
┌───────────────────────┐
│      Generation       │  ← 要素命中率 / Faithfulness / Citation
└───────────┬───────────┘
            ↓
   报告生成 Workflow
     （Python 算数，LLM 写字）
            ↓
┌───────────────────────┐
│       Business        │  ← 时间 / 修改率 / 成本
└───────────┬───────────┘
            ↓
     Failure Analysis
            ↓
      Iteration Loop
```

### 模块清单(七个,各自独立)

| # | 模块 | 职责 | 输入 → 输出 |
|---|---|---|---|
| 1 | 语料采集 | 采集并规整公开资料 | 网页/PDF → 规整 markdown |
| 2 | 切片器 | 文档切块(3 种策略可切换) | markdown → chunks |
| 3 | 向量化存储 | 文本块转向量入库 | chunks → ChromaDB |
| 4 | 检索 | 问题 → 相关块 + 相似度分 | query → chunks + scores |
| 5 | 生成 | 检索结果 + 问题 → 答案 | context → answer |
| 6 | 报告工作流 | 机场名 → 报告初稿 | airport → report |
| 7 | **评估** | 量化对比各方案效果 | 方案 → 指标表 |

**评估模块是项目核心,不是附属功能。**

## 四、数据来源与语料策略

### 4.1 公开可得来源(优先级排序)

| 来源 | 内容 | 可得性 |
|---|---|---|
| CAPSE 官网(capse.net) | 公开报告页、指标说明 | 高 |
| 民航资源网 CARNOC | 测评报告摘要、年度榜单 | 高 |
| 新闻报道 | 具体得分、排名、指标数据 | 高 |
| 民航局公开报告 | 服务标准、行业数据 | 中 |
| 机场/航司年报 | 服务相关数据 | 中 |
| 学术论文 | CAPSE 数据引用、方法论 | 中 |
| 机场官网服务标准 | 服务项定义 | 中 |

### 4.2 ⚠️ Day 0 前置验证(必须做)

**必须先摸清语料实际规模,再决定测试集规模。**

理由:聚合型问题需要**多期报告**支撑,若公开语料不足,方案需调整。

验证动作:
1. 按上表逐源采集,统计可得文档数与覆盖时间跨度
2. 判断:能否支撑 60 题?能否支撑跨期聚合题?
3. **若不足**,按序处理:
   - 扩大来源(加入方法论类、标准类文档)
   - 缩减聚合型题量
   - 调整测试集规模(下限 40 题)
4. **红线:绝不用编造数据凑题。** 语料不足就在作品中如实说明边界

### 4.3 语料处理原则

- 保留来源、日期、机构等元数据(用于引用追溯)
- **表格单独处理**:表格是 RAG 的重灾区(Case 2),需专门记录解析方式
- 保留文档结构(标题层级),供切片策略 B 使用

## 五、测试集设计

### 5.1 规模与构成(目标 60 题)

| 类型 | 数量 | 说明 |
|---|---:|---|
| 事实型 | 20 | 单一事实,如"某指标得分是多少" |
| 对比型 | 12 | 两个对象比较 |
| 聚合型 | 10 | 需跨文档/跨期汇总 |
| 推理型 | 5 | 需基于数据做判断 |
| 生成型 | 5 | 报告初稿质量 |
| **不可答型** | **8** | **负样本,正确行为是拒答** |

> **不可答型为本次新增(补充意见①)。** 没有负样本,拒答机制实验无意义。

### 5.2 每题标注内容

```json
{
  "id": "Q001",
  "type": "fact",
  "question": "2024 年机场服务与设施一级指标平均分是多少?",
  "golden_answer": "4.33 分",
  "source_chunks": ["doc_2024_report#chunk_12"],
  "key_elements": ["4.33 分", "机场服务与设施", "一级指标"],
  "answerable": true
}
```

- `key_elements`:**关键要素清单**,命中几个算几分(**比 LLM 自评可靠**)
- `source_chunks`:标注答案出处,用于算 **Recall@K**
- `answerable`:负样本标记

### 5.3 测试集的诚实性要求

- 题目从语料中真实提取,**不臆造**
- 标准答案有明确出处
- 判定标准事先写死,不事后修改(防止凑数)

## 六、评估指标体系(四层)

### 第一层:Retrieval(检索质量)

| 指标 | 定义 | 计算 |
|---|---|---|
| **Recall@K** | 含答案的文档块是否出现在 Top-K | 自动 |
| **Context Precision** | 检索结果中有多少真正有用 | 自动 |

必须同时看两个:可能出现 **Recall@8 很高但 Top-8 大量无关内容**的情况,这种检索质量不能算好。

### 第二层:Generation(生成质量)

| 指标 | 定义 | 计算 |
|---|---|---|
| **要素命中率** | 命中关键要素数 / 总要素数 | 自动(字符串/规则匹配) |
| **Faithfulness** | 是否有事实性幻觉 | **数值部分全自动 + 非数值部分抽样判定** |
| **Citation Correctness** | 引用是否真的支持结论 | 自动 + 抽样复核 |

**Faithfulness 的自动化方案(补充意见③)**:

报告与回答中所有数值均由 Python 计算,因此可写**数值校验器**:抽取 LLM 输出中的全部数字,逐个核对是否存在于 Python 计算结果集。

→ **数值幻觉率可全自动计算**,不依赖 LLM 自评。

非数值幻觉(如把"安检"说成"行李服务")用抽样 + 人工判定,并在作品中标注抽样比例。

### 第三层:Business(业务价值)

| 指标 | 类型 | 说明 |
|---|---|---|
| 报告生成耗时 | 客观 | 程序计时 |
| **数据事实覆盖率** | 客观 | Python 自动算:报告覆盖的必需数据项比例 |
| **需人工补写段落占比** | 客观 | 初稿中标记为需补写的段落比例 |
| **引用可验证率** | 客观 | 引用能被源文档验证的比例 |
| 人工修改时间 | **主观** | 模拟业务方审校,单人,如实标注 |
| 人工审核通过率 | **主观** | 模拟业务方审校,单人,如实标注 |

> **诚实性要求(补充意见②)**:主观指标在作品集中必须标注"**由本人模拟业务方审校,单人主观评估,非真实业务数据**"。
> 宁可写明是模拟,也不让数字看着漂亮但来路不明。

### 第四层:Cost(成本)

- Token 消耗(输入/输出分别统计)
- 单次问答成本
- 单份报告成本

## 七、对比实验设计

### 7.1 固定变量法(核心纪律)

做任何实验时,**固定**:
- Embedding 模型
- LLM
- Top-K
- Threshold
- 测试集
- Prompt
- 评估方法

**只改变一个变量。**

### 7.2 实验一:切片策略对比

固定 K=5,比较:

| 策略 | 定义 |
|---|---|
| **A 固定长度** | chunk_size=500 tokens, overlap=100 |
| **B 按标题层级** | 保持一/二/三级标题结构 |
| **C 按指标结构** | 让「指标名 + 数值 + 解释」留在同一块 |

观察:Recall@K、Context Precision、要素命中率

### 7.3 实验二:Top-K 对比

用最优切片策略,比较 **K = 3 / 5 / 8**

### 7.4 实验三:相似度阈值对比

比较 **Threshold = 0.6 / 0.7 / 0.8**

### 7.5 实验四:拒答机制对比

比较 **不设阈值 / 0.6 / 0.7 / 0.8**,在**含负样本的完整测试集**上观察:

| 观察项 | 说明 |
|---|---|
| 错误回答率 | 该拒答却回答了 |
| 拒答率 | 拒答的比例 |
| 有效准确率 | 在可答题上的表现 |

**这是体现产品思维与风险控制的关键实验。**

### 7.6 迭代记录格式

```text
v1  固定长度切片, K=5          → Recall@5 58%  要素命中 41%
    问题:指标数据被切断,一半答案找不到

v2  改按标题层级切片            → Recall@5 74%  要素命中 63%
    问题:跨报告对比型仍差

v3  按指标结构切片 + K=8        → Recall@5 86%  要素命中 79%
    问题:推理型仍弱,原因:需跨文档聚合
```

**"为什么改"比"改了涨了"重要。**

## 八、报告生成工作流

### 8.1 核心原则

> **能由程序计算的内容,不交给 LLM 计算。**

| Python 负责 | LLM 负责 |
|---|---|
| 平均分、同比、环比 | 总结 |
| 指标排序、TOP/Bottom | 归纳 |
| 差值、百分比变化 | 解释 |
| 数据事实提取 | 生成建议文字 |

### 8.2 报告结构

```text
数据事实 → 指标变化 → 证据引用 → 问题解释 → 改进建议
   ↑                                    ↑
 Python 算                          LLM 写
```

### 8.3 流程

1. 输入机场名
2. 检索该机场全部相关指标 → Python 汇总计算
3. Python 生成「数据事实」层(得分、排名、差值)
4. LLM 基于数据事实生成「解释」与「建议」
5. 输出带数据引用的报告初稿

**这样既减少幻觉,也更接近真实企业工作流。**

## 九、失败案例分析(专门章节,至少 3 类)

### Case 1:跨文档问题
- **现象**:问题需同时利用多份报告
- **失败原因**:单次检索无法召回全部必要证据
- **验证方法**:对比 Recall@K 与实际正确答案

### Case 2:表格问题
- **现象**:正文有相关描述,但真正答案在表格中
- **失败原因**:PDF/表格结构在解析或切片中丢失
- **验证方法**:检查源 chunk 中表格是否完整

### Case 3:推理问题
- **现象**:正确数据已检索到,但模型推理错误
- **失败原因**:Retrieval 正常,**Generation 出错**
- **验证方法**:分离两层评估指标定位

> 三个案例共同证明:**我知道系统为什么失败,而不是只知道怎么让它成功。**

## 十、边界与生产差距分析

### 10.1 适合 AI 的环节
- 数据汇总、指标提取
- 报告初稿生成
- 常规事实问答

### 10.2 必须人工审核的环节
- 对外发布的最终结论
- 涉及评价性质的判断
- 低置信度(触发拒答)的问题

### 10.3 上生产还缺什么

| 缺口 | 说明 |
|---|---|
| 权限控制 | 不同角色可见数据范围 |
| 增量更新 | 新报告发布后的知识库更新 |
| 评测集维护 | 持续扩充与校准 |
| 审核机制 | 人工复核工作流 |
| 成本控制 | 规模化后的成本优化 |
| 监控告警 | 效果衰减检测 |
